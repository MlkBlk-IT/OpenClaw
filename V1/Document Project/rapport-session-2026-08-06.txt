3. METHODES DE RECHERCHE UTILISEES
====================================================================

Recherche web utilisee a 4 reprises distinctes, chacune pour verifier
une affirmation avant de l'utiliser (pas d'assertion sans verification):

  a) Format reel SKILL.md OpenClaw (docs.openclaw.ai) - a determine que
     le contenu demande n'etait PAS un skill (procedure invocable) mais
     une regle de gouvernance permanente -> reoriente vers knowledge/.

  b) Format reel knowledge/*.md - aucune structure officielle "knowledge/"
     trouvee dans docs.openclaw.ai. Conclusion: convention perso de
     l'utilisateur, pas une fonctionnalite native. Confirme ensuite par
     capture d'ecran + contenu reel de security.md/routing.md fournis
     directement par l'utilisateur - le format a ete deduit de ces
     fichiers reels, jamais invente.

  c) OWASP LLM01 / GenAI Top 10 (genai.owasp.org, OWASP Cheat Sheet
     Series) - standard industrie pour separation instruction/donnee
     et gestion des contenus non-fiables. Utilise pour cross-verifier
     le contenu de firewall.md contre les pratiques etablies.

  d) Best practices agents locaux/subagents OpenClaw (docs.openclaw.ai,
     github.com/openclaw/openclaw) - a confirme le pattern officiel
     "task/label = data, pas instruction" pour les sub-agents, et la
     regle no-nested-fanout (un sub-agent ne peut pas en spawner un
     autre) - integree dans AGENTS.md(local).

  e) Guardrails 2026 / data-exfiltration prevention (Kiteworks, Webyot,
     Improvado) - a etabli une limite honnete: un guardrail textuel
     seul reste probabiliste, jamais un vrai hard-stop. Cette limite
     est documentee explicitement dans AGENTS.md(local) plutot que
     de presenter le guardrail comme infaillible.

====================================================================
4. DECISIONS PRISES ET JUSTIFICATION
====================================================================

4.1 firewall.md cree dans knowledge/ (pas skills/)
    Raison: le contenu (zero-trust content-boundary) est un
    comportement permanent, pas une procedure declenchee a la demande.
    Un skill OpenClaw = invocable pour UNE tache; ceci s'applique a
    chaque tour.

4.2 Classification binaire DATA/INSTRUCTION (pas 5 categories)
    Le standard academique (arxiv 2606.31639) recommande des categories
    typees (instruction/document/tool-output/memoire/policy). Choix:
    garder le binaire decisionnel simple, ajouter les sous-types comme
    tag de tracabilite (log-only) sans changer la logique de decision.
    Compromis explicite entre rigueur academique et lisibilite/maintenabilite
    pour un systeme solo, pas une equipe.

4.3 Frontiere interne Main<->local traitee comme frontiere externe
    Justification empirique directe: l'incident-canonical a montre
    qu'une fabrication peut se produire sans compromission externe.
    Donc l'appartenance au systeme (local = agent de confiance
    operationnelle) ne doit pas donner d'immunite de classification.

4.4 Regle HARD-GUARDRAIL (info sensible) repetee dans 3 fichiers
    (SOUL.md, AGENTS.md, firewall.md) + rappel dans USER.md
    Redondance voulue et confirmee explicitement par l'utilisateur,
    pas une duplication a nettoyer. Rationale: la meme regle depuis
    plusieurs points d'entree reduit la probabilite qu'un chemin
    d'execution la contourne completement.

4.5 Limite honnete documentee dans le guardrail lui-meme
    Ligne ajoutee explicitement: "regle-textuelle=probabiliste... reduit
    le risque, elimine pas. hardening structurel = hors-scope, a
    evaluer separement." Choix de ne pas presenter le guardrail comme
    une garantie absolue, ce qui aurait ete techniquement faux et aurait
    reproduit l'erreur de l'incident-canonical (confiance excessive dans
    une regle textuelle).

4.6 Routing @local: documente comme config custom, pas comme feature
    officielle garantie
    La recherche (docs.openclaw.ai/concepts/multi-agent) confirme un
    mecanisme de bindings + mentionPatterns, mais pas explicitement un
    bypass ingress ponctuel dans un chat partage. Ecrit tel quel plutot
    que suppose confirme.

Series d'instructions supplementaires integrees au fur et a mesure
(bypass ingress @local, restriction skills red-team, priorite
orchestrateur-local avant fallback cloud, regle absolue sur les
informations sensibles). Cette derniere a ete la plus travaillee:
premiere version jugee insuffisamment stricte, renforcee en butee
avec liste explicite de tentatives de contournement (impersonation,
ordre direct, invocation de policy, bypass graduel), puis dupliquee
intentionnellement sur 3 fichiers plus un rappel dans USER.md pour
reduire le risque qu'un seul point de defaillance suffise a la
contourner.

Tous les patches ont ete appliques via scripts PowerShell suivant
le protocole deja etabli (backup/validate/write/validate/rollback),
avec confirmation manuelle systematique avant chaque ecriture-disque.
Aucune donnee perdue, un seul correctif necessaire en cours de route
(probleme de regex, pas de contenu).
